# Phase 10: System integration and ship — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **Subagents are not used on this project** (session rule) — inline execution only.

**Goal:** Make the app survive the machine it runs on — recover from sleep, wake and unlock; start with Windows if the user wants it; and carry a real app icon — so the single-file exe is something you'd hand to someone.

**Architecture:** The same split every phase since 7a has used. `SystemResumeTrigger` decides *which* Windows events count as a resume — a pure rule over two enums, exhaustively tested. `SystemEventsWatcher` is the thin subscriber that can't be tested because `SystemEvents` is static, and it does nothing but consult that rule, log, and forward. `StartupManager` owns the HKCU Run key, with an injectable key path so tests never touch the real one. The launch-at-login checkbox joins the Settings window through `SettingsEditor`, alongside the nine settings already there.

**Tech Stack:** WPF on `net10.0-windows10.0.17763.0`. `Microsoft.Win32.SystemEvents` and `Microsoft.Win32.Registry` — **both already available**, no package reference needed (verified by compiling a probe against this exact TFM before this plan was written).

## Global Constraints

- **Do not add anything to `OnDeck.Core`.** `HandleSystemResumeAsync()` already exists, already debounces 30 s, and already invalidates the monitor's timecodes. Phase 10 calls it; it does not change it.
- `OnDeck.Core` keeps **zero** package references. Verify with `grep -c PackageReference windows/src/OnDeck.Core/OnDeck.Core.csproj` → `0`.
- **Never write to the real `Run` key from a test.** `StartupManager` takes an injectable key path for exactly this reason; tests use a scratch subkey under `HKCU\Software\onDeck\` and delete it afterwards. A test that adds a real startup entry to the owner's machine is a bug, not a test.
- **Kill the app before every build and test run** — the process is named **`onDeck`**:
  `powershell -NoProfile -Command "Get-Process -Name 'onDeck' -ErrorAction SilentlyContinue | Stop-Process -Force"`
  Always confirm **TWO `Passed!` lines**, one per test project (HANDOFF §3).
- Single-file publish stays green:
  `dotnet publish windows/src/OnDeck.App -c Release -r win-x64 --self-contained -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:EnableCompressionInSingleFile=true`
- **Do not touch the DWM backdrop path**, and **do not remove `ThemeMode="System"` from `App.xaml`** (`ACRYLIC-OPEN-ISSUE.md`, parked by owner decision).
- **Two traps from HANDOFF §6 govern this phase.** Trap 6: never block the Dispatcher on a Core task — `SystemEvents` handlers arrive on a **background thread**, so marshal, don't `.Wait()`. Trap 1 (XAML): a `Style` on a control replaces the Fluent implicit style wholesale — the new checkbox must be styled like its two neighbours, which means not styled at all.
- Commits go **directly to `main`**, one per task. **Never append `Co-Authored-By` or any AI-attribution trailer.**
- Commands run from the repo root (`c:\Users\brian\Code\onDeck`). Always pass `windows/OnDeck.slnx`.
- Launching the built app locally to verify is allowed. **Installing it is not.** **Don't trust automated screen capture** — ask the owner to look.

## Scope

**In:** `SystemEventsWatcher` + `SystemResumeTrigger` wired to `HandleSystemResumeAsync`; `StartupManager` over the HKCU Run key with a self-heal for a moved exe; a launch-at-login checkbox in the Settings window's Display card; a real multi-resolution app icon generated by the existing `IconGen` tool and set as `<ApplicationIcon>` and the Settings window's `Icon`.

**Out (deliberate):**
- **The clean-machine run.** Phase 10's ship gate is the single-file exe on a Windows 11 box with no .NET installed. **The owner has no VM or second machine available**, so this carries into Phase 11's QA list, flagged in HANDOFF as the one unverified assumption in the ship story. - **An uninstaller.** Nothing installs, so nothing uninstalls. If one is ever added it must call `ToastNotificationManagerCompat.Uninstall()` and remove the Run value (spike FINDINGS.md, finding 2).

## Task 1: Which system events mean "recover"

**Files:**
- Create: `src/OnDeck.App/Platform/SystemResumeTrigger.cs`
- Create: `tests/OnDeck.App.Tests/SystemResumeTriggerTests.cs`

**Interfaces:**
- Produces: `static class SystemResumeTrigger` with `bool IsResume(PowerModes mode)` and `bool IsResume(SessionSwitchReason reason)`.
- Consumed by: Task 2's `SystemEventsWatcher`.

**Why this exists.** `AppState.swift:524-539` registers **three** observers — `didWakeNotification`,
`sessionDidBecomeActiveNotification`, and the `com.apple.screenIsUnlocked` distributed notification.
Windows delivers the equivalents through two events carrying enums with eleven values between them,
and picking the wrong subset fails in one of two silent ways: too few and the app comes back from
sleep with stale data and no error; too many and every screen lock triggers a full roster resync,
schedule refetch and monitoring restart. Core's 30-second debounce hides the second failure locally
while the work still happens.

**The mapping**, chosen deliberately:

| Swift observer | Windows | Why |
|---|---|---|
| `didWakeNotification` | `PowerModes.Resume` | The machine woke |
| `com.apple.screenIsUnlocked` | `SessionSwitchReason.SessionUnlock` | The screen was unlocked |
| `sessionDidBecomeActiveNotification` | `SessionSwitchReason.ConsoleConnect`, `RemoteConnect` | Our session became the active one again — local fast-user-switch or an RDP reattach |

Everything else is deliberately **not** a resume: `SessionLock`, `ConsoleDisconnect`,
`RemoteDisconnect`, `SessionLogoff` and `SessionRemoteControl` are departures, not returns;
`SessionLogon` cannot apply to a process that is already running in that session; and
`PowerModes.Suspend` / `StatusChange` are the going-to-sleep and battery-state signals.

```csharp
using Microsoft.Win32;

namespace OnDeck.App.Platform;

/// <summary>
/// Which Windows system events count as "we've been away — recover". The port of the three
/// observers <c>AppState.swift:524-539</c> registers: <c>didWakeNotification</c>,
/// <c>sessionDidBecomeActiveNotification</c> and <c>com.apple.screenIsUnlocked</c>.
/// <para>
/// Kept apart from <see cref="SystemEventsWatcher"/> because <c>SystemEvents</c> is static and
/// cannot be raised from a test, while getting this set wrong fails silently in both directions:
/// too few and the app returns from sleep with stale data, too many and every screen lock starts
/// a roster resync, a schedule refetch and a monitoring restart.
/// </para>
/// </summary>
public static class SystemResumeTrigger
{
    public static bool IsResume(PowerModes mode) => mode == PowerModes.Resume;

    public static bool IsResume(SessionSwitchReason reason) => reason is
        SessionSwitchReason.SessionUnlock       // com.apple.screenIsUnlocked
        or SessionSwitchReason.ConsoleConnect   // sessionDidBecomeActive - fast user switch back
        or SessionSwitchReason.RemoteConnect;   // ... or an RDP reattach
}
```

## Task 2: The watcher, and wiring it to Core

**Files:**
- Create: `src/OnDeck.App/Platform/SystemEventsWatcher.cs`
- Modify: `src/OnDeck.App/App.xaml.cs`

**Interfaces:**
- Consumes: `SystemResumeTrigger` (Task 1); `ShellLog`; `AppOrchestrator.HandleSystemResumeAsync()`.
- Produces: `sealed class SystemEventsWatcher(Action<string> onResume) : IDisposable`.

**Why there is no test for this class.** `SystemEvents` is a static event source backed by a
process-wide hidden window; a test cannot raise `PowerModeChanged`. Everything decidable was moved
to Task 1, and what remains is two lambdas, a log line and an unsubscribe. The verification is a
log line after a real lock/unlock, in Task 6.

**Two things this must get right.**

1. **Handlers arrive on a background thread.** `HandleSystemResumeAsync` is Core, and Core runs on
   one logical thread — the Dispatcher. Calling it from the event thread breaks the guarantee the
   race guards depend on. Marshal with `InvokeAsync`, and **never** `.Wait()` on the result
   (HANDOFF §6, trap 6: Core has no `ConfigureAwait(false)`, so blocking the Dispatcher on a Core
   task deadlocks).
2. **`SystemEvents` holds its handlers for the life of the process.** A handler that is never
   removed keeps the watcher — and the whole shell graph behind its closure — alive. Unsubscribe in
   `Dispose`, and dispose it in `OnExit` beside the tray icon.

- [ ] **Step 1: Implement the watcher**

Create `src/OnDeck.App/Platform/SystemEventsWatcher.cs`:

```csharp
using Microsoft.Win32;

namespace OnDeck.App.Platform;

/// <summary>
/// Port of <c>setupSystemResumeHandler</c> (<c>AppState.swift:524-539</c>): listens for the
/// machine waking and for our session coming back, and calls back so the shell can ask Core to
/// recover. <see cref="SystemResumeTrigger"/> owns which events qualify.
/// <para>
/// <b>The callback runs on a background thread.</b> Whatever it does must marshal to the
/// Dispatcher before touching Core.
/// </para>
/// </summary>
public sealed class SystemEventsWatcher : IDisposable
{
    private readonly Action<string> _onResume;
    private readonly PowerModeChangedEventHandler _power;
    private readonly SessionSwitchEventHandler _session;

    public SystemEventsWatcher(Action<string> onResume)
    {
        _onResume = onResume;

        _power = (_, e) =>
        {
            if (SystemResumeTrigger.IsResume(e.Mode)) Raise($"power:{e.Mode}");
        };

        _session = (_, e) =>
        {
            if (SystemResumeTrigger.IsResume(e.Reason)) Raise($"session:{e.Reason}");
        };

        SystemEvents.PowerModeChanged += _power;
        SystemEvents.SessionSwitch += _session;

        ShellLog.Append("[System] resume observers registered (power, session)");
    }

    private void Raise(string reason)
    {
        // The only evidence these fire at all: nobody is attached to a debugger when the lid
        // closes. Swift logs the same thing at .notice.
        ShellLog.Append($"[System] resume: {reason}");
        _onResume(reason);
    }

    public void Dispose()
    {
        // SystemEvents keeps its subscriber list for the life of the process, so a handler that
        // is never removed pins this object and everything its callback closes over.
        SystemEvents.PowerModeChanged -= _power;
        SystemEvents.SessionSwitch -= _session;
    }
}
```

## Task 3: Launch at login

**Files:**
- Create: `src/OnDeck.App/Platform/StartupManager.cs`
- Create: `tests/OnDeck.App.Tests/StartupManagerTests.cs`

**Interfaces:**
- Produces: `sealed class StartupManager(string? keyPath = null, string? executablePath = null)` with `const string DefaultKeyPath`, `const string ValueName`, `string CommandLine`, `bool IsEnabled`, `bool IsCurrent`, `void SetEnabled(bool)`.
- Consumed by: Task 4's `SettingsEditor` and Task 5's composition root.

**Why the key path is injectable.** The only honest way to test registry code is against the
registry — but the real value lives under
`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, and a test that writes there adds a genuine
startup entry to the owner's machine and leaves it if the run is interrupted. The constructor takes
the path so tests can point at a scratch subkey and delete it afterwards. **A test must never use
the default path.**

**Why `IsCurrent` exists.** The Run value is an absolute path to the exe. Debug and Release builds
live at different paths, and a published copy at a third — so the value goes stale the moment the
exe moves, and Windows silently fails to start a program that isn't there. This is the same
dangling-registration problem the toast COM entry has (spike FINDINGS.md, finding 2), and the same
answer: re-register on launch when it's enabled but stale (Task 5).

**Why it isn't in `ISettingsStore`.** `PORT_PLAN.md` scopes launch-at-login as shell-only,
alongside the floating-panel frame. The truth lives in the registry — a user can remove the entry
through Task Manager's Startup tab, and `settings.json` would then be lying. Reading the registry
every time is what keeps the checkbox honest.

```csharp
using Microsoft.Win32;

namespace OnDeck.App.Platform;

/// <summary>
/// Launch at login: one value under the current user's <c>Run</c> key. Default off
/// (<c>PORT_PLAN.md</c> Decision 3).
/// <para>
/// Deliberately outside <see cref="OnDeck.Core.ISettingsStore"/> — <c>PORT_PLAN.md</c> scopes
/// launch-at-login as shell-only, like the floating-panel frame. The truth lives in the registry:
/// a user can remove the entry from Task Manager's Startup tab, and a copy in
/// <c>settings.json</c> would then be lying. Every read goes to the registry.
/// </para>
/// <para>
/// The macOS app has no counterpart — this is a Windows-only addition.
/// </para>
/// </summary>
public sealed class StartupManager(string? keyPath = null, string? executablePath = null)
{
    public const string DefaultKeyPath = @"Software\Microsoft\Windows\CurrentVersion\Run";

    public const string ValueName = "onDeck";

    private readonly string _keyPath = keyPath ?? DefaultKeyPath;

    private readonly string _executablePath = executablePath ?? Environment.ProcessPath ?? "";

    /// <summary>
    /// The value Windows runs. Quoted: an unquoted path is parsed at the first space, so
    /// <c>C:\Program Files\onDeck\onDeck.exe</c> would try to launch <c>C:\Program</c>.
    /// </summary>
    public string CommandLine => $"\"{_executablePath}\"";

    public bool IsEnabled => Read() is not null;

    /// <summary>
    /// Whether the stored command points at <em>this</em> exe. False after the exe moves — Debug,
    /// Release and a published copy all live at different paths, and Windows silently fails to
    /// start a program that isn't there.
    /// </summary>
    public bool IsCurrent => string.Equals(Read(), CommandLine, StringComparison.OrdinalIgnoreCase);

    public void SetEnabled(bool enabled)
    {
        try
        {
            if (enabled)
            {
                using var key = Registry.CurrentUser.CreateSubKey(_keyPath);
                key.SetValue(ValueName, CommandLine, RegistryValueKind.String);
            }
            else
            {
                using var key = Registry.CurrentUser.OpenSubKey(_keyPath, writable: true);
                key?.DeleteValue(ValueName, throwOnMissingValue: false);
            }

            ShellLog.Append($"[Startup] launch at login {(enabled ? "enabled" : "disabled")}");
        }
        catch (Exception exception) when (exception is UnauthorizedAccessException or IOException
                                              or System.Security.SecurityException)
        {
            // Group policy can lock the Run key. The checkbox re-reads the registry on the next
            // render, so it corrects itself rather than lying about what happened.
            ShellLog.Append($"[Startup] could not write the Run value: {exception.Message}");
        }
    }

    private string? Read()
    {
        try
        {
            using var key = Registry.CurrentUser.OpenSubKey(_keyPath);
            return key?.GetValue(ValueName) as string;
        }
        catch (Exception exception) when (exception is UnauthorizedAccessException or IOException
                                              or System.Security.SecurityException)
        {
            return null;
        }
    }
}
```

`StartupManager.cs` needs `using System.IO;` for `IOException` — WPF's implicit usings omit
`System.IO` (HANDOFF §5).

**Why a new icon rather than the tray one.** Owner-confirmed: the three existing `.ico`s are tray
variants — a 2 px stroke on transparency at 16/20/24/32 only. Explorer, the taskbar's jump list and
the SmartScreen dialog all want 256 px, where an upscaled 32 px frame is visibly soft, and a thin

which is exactly how the ICO format encodes a 256 px frame. Don't "fix" that line.

**The stale Run value.** `StartupManager.IsCurrent` exists for this; the composition root heals it
on launch, the same way the Toolkit rewrites the toast COM registration on every `Show()`.

```csharp
byte[] RenderAppPng(int size)
{
    var disc = new SolidColorBrush(discColour);
    disc.Freeze();

    // White on the disc, and a touch heavier than the tray stroke so it survives the shrink to
    // 62% below without dissolving at 16 px.
    var pen = new Pen(new SolidColorBrush(Colors.White), 2.4)
    {
        StartLineCap = PenLineCap.Round,
        EndLineCap = PenLineCap.Round,
        LineJoin = PenLineJoin.Round,
    };
    pen.Freeze();

    var visual = new DrawingVisual();
    using (var context = visual.RenderOpen())
    {
        context.PushTransform(new ScaleTransform(size / 24.0, size / 24.0));
        context.DrawEllipse(disc, null, new Point(12, 12), 12, 12);

        // Shrink the 24-unit ball about the centre so it sits inside the disc with a margin.
        context.PushTransform(new TranslateTransform(12, 12));
        context.PushTransform(new ScaleTransform(0.62, 0.62));
        context.PushTransform(new TranslateTransform(-12, -12));
        foreach (var data in outline) context.DrawGeometry(null, pen, Geometry.Parse(data));
        context.Pop();
        context.Pop();
        context.Pop();

        context.Pop();
    }

    var bitmap = new RenderTargetBitmap(size, size, 96, 96, PixelFormats.Pbgra32);
    bitmap.Render(visual);

    var encoder = new PngBitmapEncoder();
    encoder.Frames.Add(BitmapFrame.Create(bitmap));

    using var stream = new MemoryStream();
    encoder.Save(stream);
    return stream.ToArray();
}
```

## Deviations from the Swift original

*(Filled in during execution. The entries below are the ones this plan commits to up front.)*

| Deviation | Why |
|---|---|
| Launch at login has no macOS counterpart | The Mac app doesn't offer it. `PORT_PLAN.md` Decision 3 adds it for Windows, default off |
| Launch at login lives in the registry, not `ISettingsStore` | `PORT_PLAN.md` scopes it shell-only, like the floating-panel frame. The user can remove the entry from Task Manager's Startup tab, so a copy in `settings.json` would go stale and lie |
| `SettingsEditor.LaunchAtLogin` re-reads its backing store on every get | The other nine read a cached snapshot; this one can be changed from outside the app while the window is open |
| Swift's three resume observers become two Windows events over five enum values | `didWakeNotification` → `PowerModes.Resume`; `com.apple.screenIsUnlocked` → `SessionUnlock`; `sessionDidBecomeActive` → `ConsoleConnect` + `RemoteConnect` (local switch and RDP reattach) |
| `MemoryPressureRelief.releaseReclaimablePages()` in the resume path not ported | macOS-only, and already excluded by `PORT_PLAN.md` |
| The Run value is re-registered on launch when it points elsewhere | The value is an absolute path with no counterpart to the Toolkit's automatic COM re-registration; without this, launch-at-login silently stops working after the exe moves |
| A new app icon rather than reusing a tray variant | The tray `.ico`s stop at 32 px and are strokes on transparency; Explorer and SmartScreen render at 256 px against arbitrary backgrounds. Owner-confirmed |
| No test raises a `SystemEvents` event | It is a static, process-wide event source that cannot be raised from a test. Everything decidable is in `SystemResumeTrigger`; what's left is two lambdas and an unsubscribe, verified by a log line after a real unlock |

## Notes carried forward

- **The clean-machine run is deferred, not done.** The single-file exe has never been run on a
  Windows 11 machine without the .NET SDK installed. Publish is self-contained and green, so the
  risk is low, but it is the one untested assumption in the ship story. It belongs at the top of
  Phase 11's QA list.
- **A Debug build that enables launch-at-login writes the Debug path.** That is correct behaviour —
  the value points at the exe that wrote it — but it means the owner's Run entry will point into
  `bin/Debug` until they enable it from a published copy. Worth mentioning to them rather than
  silently rewriting.
- **`ToastNotificationManagerCompat.Uninstall()` and the Run value** are the two things an
  uninstaller would have to clean up. Nothing installs today, so nothing does.
